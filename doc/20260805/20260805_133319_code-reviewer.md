## 결정 사항 (선택지가 있었던 지점)

### 1. AC-011-3 — 수용 / requirements 정정 / 구현 변경 중 → **수용 + requirements 정정**

세 실험(A: index에서 back, B: naver에서 back, C: appFinish)을 직접 수행해 판정했다. C가 `finish()` 경로의 정상 동작을 증명하고, A와 B가 갈린다는 사실이 `canGoBack` 상태 관리의 실제 동작을 증명한다. 원인은 API 31+ 플랫폼 동작 변경이며 구현 결함이 아니다. 강제 `finish()`는 오히려 REQ-011의 "통상대로"에서 이탈한다.

**developer 로그에 없는 사실을 하나 더 찾았다:** `minSdk = 26`이라 **API 30 이하 기기에서는 AC-011-3 원문이 그대로 성립한다.** 즉 이것은 "항상 실패하는 기준"이 아니라 **버전에 따라 갈리는 기준**이다. 이 발견이 MAJOR-1의 수정 지시 내용(주석에 버전 분기를 명시하라)과 QA 인계 1번 항목의 근거가 됐다.

### 2. AC-002-2 — ⓐ 수용 / ⓑ exclude / ⓒ 버전 하향 중 → **ⓐ 수용, evaluator 재승인 불요**

dex를 직접 열어 Compose UI 툴킷이 한 클래스도 없음을 확인했다. REQ-002의 의도는 완전히 충족된다. ⓑ·ⓒ는 승인된 의존성 결정(L-03)을 바꿔 evaluator 재승인이 필요한데, 얻는 것은 문언 충족뿐이고 잃는 것은 navigationevent 동작 리스크(ⓑ) 또는 미검증 버전 조합(ⓒ)이다. **비용이 이익을 넘는다고 판단했다.**

**단, 코드에 기록을 남기게 했다(MINOR-6).** 유입 경로가 어디에도 적혀 있지 않으면 다음 사람이 의존성 트리의 `androidx.compose`를 보고 `exclude`로 "고치다가" navigationevent를 깬다. 판정이 ⓐ이기 때문에 오히려 이 주석이 필요해졌다.

### 3. CHANGES_REQUESTED를 주석 1건으로 낼 것인가 → **냈다**

스킬 기준상 MAJOR 1건 이상이면 CHANGES_REQUESTED다. 다만 **모호한 반려를 피하라**는 지시에 따라 지적을 파일·라인과 함께 "무엇을 어떻게 고칠 것인지" 3개 요소로 구체화했고, **재작업 범위가 주석 2곳뿐이며 그 외에는 손댈 것이 없다**고 review.md 첫머리에 명시했다. 재작업 루프 비용을 최소화하기 위해 함께 처리할 MINOR도 1건(MINOR-6, 같은 성격)만 지정했다.

### 4. MINOR-1(확장 설치 실패 시 크래시)·MINOR-8(프로브가 release에도 실행)을 MAJOR로 올릴 것인가 → **올리지 않았다**
