### 1. 인계값을 옮겨 적지 않고 전부 재측정했다 (V7) — 인계 문서 정정 3건

### 2. AGP / Gradle wrapper 조합을 **추측하지 않고 실제로 빌드해서** 확정했다 (rev.2 이슈 12 해소)

rev.2는 "AGP를 먼저 고르고 wrapper를 생성할 것"이라는 지침만 남기고 조합을 [미확인]으로 넘겼다. 스크래치패드에 실제 Android 프로젝트를 만들어 세 조합을 돌렸다.

| 조합 | 결과 |
|:--|:--|
| AGP 9.3.1 + Gradle **9.3.1** (=시스템 gradle) | **실패.** `NoClassDefFoundError: org/gradle/features/binding/ProjectTypeBinding` |
| AGP 9.3.1 + Gradle 9.6.1 + JDK 21 | **성공** (APK 생성 + JaCoCo 리포트). 단 `org.jetbrains.kotlin.android`를 적용하면 **빌드 실패**(AGP 9는 Kotlin 내장), stdlib이 **2.2.10**으로 고정 |
| **AGP 8.13.2 + Gradle 8.14.5 + Kotlin 2.3.21 + JDK 21** | **성공, 채택.** APK 생성 + 커버리지 XML 생성, `kotlin-stdlib` **2.3.21** 해석 |

**첫 줄이 이 검증의 수확이다** — "시스템 gradle이 9.3.1이니 wrapper도 9.3.1"이라는 자연스러운 선택이 **실제로 죽는다는 반증**을 얻었다. rev.2가 경고만 하고 넘긴 지점이 실재하는 함정이었다.

AGP 9를 배제한 근거는 계획 §2.4에 세 가지로 적었다. 핵심은 **AGP 9의 내장 Kotlin이 2.2.10이라 GeckoView가 끌고 오는 stdlib 2.3.21과 어긋난다**는 것 — requirements.md §2.4가 [미확인]으로 남긴 "Kotlin stdlib 충돌" 리스크가 AGP 9에서는 **실제로 발생하고**, AGP 8 + KGP 2.3.21에서는 **사라진다**. `:app:dependencies`로 2.3.21 해석을 확인했다.

### 3. 커버리지 70% 경로를 설계 결정으로 환원했다 (지시 D)

rev.2 이슈 6이 경고한 지점이다. 계측 테스트는 JaCoCo 집계 밖이고(V8), REQ-010은 전량 JS라 분모에 0 기여하며, GeckoView는 실기기 없이 실행 불가다. **"어디서 벌 것인가"를 클래스 단위로 못 박기 전에, 애초에 그 클래스들이 순수 Kotlin이 되도록 설계를 바꿔야 한다**는 것이 결론이었다.

70%를 가능하게 만드는 **설계 결정 3개**를 찾아 계획에 넣었다:
1. **wire를 JSON *문자열*로 주고받는다**(§3.1). 객체를 주고받으면 Kotlin 쪽이 `org.json.JSONObject`(안드로이드 전용, JVM 테스트에서 stub)를 쓰게 되고, 그러면 `BridgeProtocol`이 JVM 테스트 불가가 되어 **70%가 원리적으로 무너진다.**
2. **`AppInfoRepositoryImpl`이 `Context`가 아니라 `versionNameProvider: () -> String?` 람다를 받는다**(D-02). `PackageManager` 호출은 `App.kt` 한 곳으로 밀어낸다. Context 격리(architecture.md)와 커버리지가 같은 방향을 가리킨다.
3. **뒤로가기를 `OnBackPressedCallback` 없이 ViewModel 이벤트로 처리한다**(D-08). androidx 타입을 ViewModel에서 몰아내는 것과 뒤로가기 로직을 JVM 테스트하는 것이 동시에 해결된다.

**JaCoCo 설정도 추측하지 않고 실행해서 확인했다.** 커스텀 `JacocoReport` 태스크(`jvmCoverageReport`)를 만들어 ① `.exec` 실측 경로(`app/build/outputs/unit_test_code_coverage/debugUnitTest/testDebugUnitTest.exec`) ② `classDirectories` 제외 규칙이 실제로 동작하는지(테스트용 `gecko/**` 패키지가 리포트에서 빠지는지) ③ XML이 생성되는지를 전부 확인했다. 계획 §7.2의 스크립트는 **그대로 돌려본 것**이다.

`kotlinx-serialization-json` 도입도 이 경로에 종속되므로, 승인 요청 사유를 "편해서"가 아니라 **"이것 없이는 70%가 원리적으로 불가능하다"**로 적었다.

### 4. 작업 순서를 "실패하면 설계가 뒤집히는 것 먼저"로 짰다 (지시 C)

Step 0(스캐폴딩) → Step 1(GeckoView 렌더) 다음에 **스파이크 3개를 연속 배치**했다:
- **Step 2**: 확장 설치 + 확장 페이지 로드 + 3단 왕복 → 실패 시 §2.7.4 폴백, **파일 구성 변경**
- **Step 3**: naver 이동 + **확장 페이지 히스토리 잔존** → 실패 시 AC-011-1 원리적 불가, 폴백
- **Step 4**: 외부 사이트 5단 경로 + **페이지 세계 주입** → 실패 시 REQ-010 재설계

UI·아키텍처 정착(Step 5~8)은 **셋이 다 통과한 뒤에** 온다. 스파이크 코드는 "최소한으로 뚫는" 코드여도 되고 Step 5에서 정식 구조로 옮긴다고 명시했다.

각 게이트는 **반증 가능한 조건**으로 썼고, AND로 묶인 조건들이 독립적으로 깨지는지 확인했다. 예: Step 3의 G3-a(index.html 재렌더)와 G3-b(복귀 후 브리지 재동작)는 독립이다 — 페이지만 그려지고 확장 메시징이 죽은 상태는 G3-a만으로 잡히지 않는다.

**실패 시 행동 규약도 각 Step에 적었다**(V9). 특히 Step 0에는 "툴체인이 §2.4와 다르게 실패하면 다른 조합을 탐색하지 말고 FAIL 반환하라"를 넣었다 — §2.4가 실측 조합이므로 그 실패는 환경 차이를 뜻하고, 임의 탐색은 범위 확장이다.

### 5. 브리지 계약을 명시적으로 정의했다 (지시 E)

impact-report가 지목한 결합점 3개(wire 스키마 / `nativeApp` 문자열 / 함수명 집합)에 대해 §3에 스키마 전문, 오류 코드 닫힌 집합, 상수화 방침, 양쪽 파일에 남길 근거 주석을 지정했다.

**§3.4에 넣은 비대칭 관찰이 이 절의 핵심이다**: 함수명을 JS에만 추가하면 네이티브가 `UNKNOWN_FUNCTION`으로 reject해 **시끄럽게** 실패하고, Kotlin에만 추가하면 JS 화이트리스트가 먼저 막아 **조용히** 실패한다. 따라서 "JS를 먼저 고쳐라"가 안전한 순서이며, 이를 양쪽 주석에 남기게 했다.

### 6. 화이트리스트 준수를 확인했다

계획의 모든 파일 경로가 impact-report의 `allowed_files`/`allowed_globs` 안에 있다. 모듈 추가와 `app/src/release/**`를 계획하지 않았다. 화이트리스트를 넓혀야 하는 유일한 시나리오는 **§2.7.4 폴백 3안(localhost 서버)** 인데, 이는 파일 경계가 아니라 **새 의존성 승인** 문제이므로 그 사실을 §9에 적고 evaluator 재승인 대상으로 넘겼다.

## 이슈 / 리스크

1. **인계 문서 두 개가 같은 항목에 서로 다른 값을 적고 있었다** (`JAVA_HOME`, PATH java). 재측정 없이 인용했다면 계획의 전제가 틀렸을 것이다. 이번 파이프라인에서 V7이 실제로 값을 건진 두 번째 사례다(impact-analyzer도 hook 로직 실행으로 3건을 건졌다).

2. **"시스템 gradle 9.3.1"은 함정이었다.** AGP 9.3.1 + Gradle 9.3.1이 실제로 죽는 것을 재현했다. rev.2 §7.4-12가 경고만 하고 넘긴 지점이 실재했다.

3. **커버리지 70%는 테스트 작성 문제가 아니라 설계 문제다.** 계획 §7.1의 클래스들이 순수 Kotlin이 아니면 목표가 **원리적으로 불가능**하다. 그래서 R-11에 "미달은 테스트 부족이 아니라 설계 오염의 신호"라고 적었다. developer가 미달 시 테스트를 더 짜는 방향으로 대응하면 시간만 쓰고 못 넘는다.

4. **[미확인] 14건을 §8에 표로 남겼다.** 추측으로 채우지 않았다. 그중 **U-01(확장 페이지 최상위 로드) · U-03(히스토리 잔존) · U-06(5단 경로)** 은 실패 시 **파일 구성이 바뀌는** 항목이며 각각 Step 2·3·4의 게이트로 배치했다.

5. **APK 크기는 [미확인]으로 남겼다.** requirements.md의 "85~95 MB"는 추정치다. Step 1 게이트에서 **실측 숫자를 기록**하도록 지정했다 — V5의 "측정 전 추정치를 문서에 쓰지 않는다. 추정치는 실측치로 굳어버린다"에 해당한다.
