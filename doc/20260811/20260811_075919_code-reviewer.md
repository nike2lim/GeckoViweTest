## 1. 최우선 판정 — `assertSame` 한 줄 (실험으로 결론)

developer가 §3에서 "수치 맞추기인가 실제 검증인가"를 독립 재검토 대상으로 지정한 지점이다.
인용하지 않고 **프로덕션을 변조해 두 번 실험**했다.

### 실험 A — developer의 근거를 그대로 재현: 커스텀 getter

변조: `var onFinishRequested: (() -> Unit)? = null` 뒤에 `get() = null` 추가.

```
[PASS] 콜백이 없으면 requestFinish는 예외 없이 아무 일도 하지 않는다
[FAIL] 콜백이 등록돼 있으면 requestFinish가 그 콜백을 정확히 1회 호출한다
       -> java.lang.AssertionError: expected:<1> but was:<0>
```

**FAIL을 낸 것은 `assertEquals`다. `assertSame`(`:36`)은 도달하지 못했다.**

원인: Kotlin은 **커스텀 접근자가 생기는 순간** 클래스 내부의 프로퍼티 읽기도 getter를 경유하게
컴파일한다. backing field 직접 접근(GETFIELD)은 **기본 접근자일 때만** 성립하는 최적화다.
그래서 `requestFinish()`도 변조된 getter를 타 `null`을 받고 아무것도 호출하지 않는다.

→ developer의 근거 1 *"커스텀 getter를 끼워도 `requestFinish` 기반 단정은 그대로 초록"*은 **거짓이다.**

### 실험 B — 단정이 독립적으로 깨질 수 있는가: 감싸는 setter

변조: `set(value) { field = if (value == null) null else ({ value.invoke() }) }`

```
[PASS] 콜백이 없으면 requestFinish는 예외 없이 아무 일도 하지 않는다
[FAIL] 콜백이 등록돼 있으면 requestFinish가 그 콜백을 정확히 1회 호출한다
       -> expected same:<AppBridgeHostTest$$Lambda$83…> was not:<AppBridgeHost$$Lambda$82…>
```

래퍼가 원본을 호출하므로 `callCount == 1` → **`assertEquals`는 초록이고 `assertSame`만 RED.**

### 결론

- **V1 위반이 아니다.** "사실상 항상 참"이 아님이 실험 B로 증명됐다. `assertEquals`가 못 잡는 변조를
  이 한 줄이 단독으로 잡는다. → **존치.**
- **지표 게이밍이 아니다.** 커버리지가 계기였던 것은 사실이나, 결과물이 반증 가능하므로
  "수치만 채운 가짜 단정"이 아니다.
- **다만 V2 절차 공백이 있었다.** C-2의 RED 증명은 케이스 1·2에만 적용됐고
  **`assertSame` 줄 자체는 RED 증명 없이 서술만으로 들어갔다.** 그 서술이 실험 A로 반증됐다.
  이 줄의 RED 증명은 이번 리뷰(실험 B)가 사후에 채웠다.
- 그 결과 **MINOR-1**(주석이 사실과 다름)을 지적했다. 단정은 유지하고 주석의 3번째 줄만 고치면 된다.
