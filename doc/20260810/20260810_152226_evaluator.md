### 2. 글롭 의미론 2종 실행 확인 (V8) — 이 배치 설계의 근거

**① Gradle Ant PatternSet**: 스크래치패드에 독립 Gradle 프로젝트를 만들고 `app/build.gradle.kts`의 **제외 목록 11개 원문을 그대로** 옮긴 뒤, 가짜 `.class` 트리(루트/`bridge/`/`di/`/`gecko/`/`data/`)에 `fileTree { exclude(coverageExclusions) }`를 적용했다.

결과: 루트의 `AppContainer.class`·`AppBridgeHost.class`는 계속 제외되고, **`bridge/AppBridgeHost.class`와 `di/AppContainer.class`는 제외되지 않아 분모에 들어온다.** `*`가 `/`를 넘지 않음이 확인됐다 — R-01 참.

**② Python fnmatch (scope-guard hook)**: `guard-impact-scope.py`를 읽어 `os.path.relpath` + `fnmatch.fnmatch` 사용을 확인한 뒤 같은 함수로 후보 경로를 실행 → `bridge/AppBridgeHost.kt`·`di/AppContainer.kt` 모두 매칭. **`*`가 `/`를 넘는다.**

두 의미론이 다르다는 전제는 참이고, **차이의 방향이 계획에 유리하다**(hook은 관대해 이동을 막지 않고, Ant는 엄격해 이동한 클래스를 분모에 넣는다).

### REJECTED를 택하지 않은 이유 (명시)

`plan-evaluation` SKILL은 "D에서 fail 하나라도 → REJECTED"라고 한다. V1-b가 형식상 D의 fail이다. 그럼에도 조건부 APPROVED로 간 판단 근거:

1. 문제의 조건은 **"필요조건일 뿐"로 이미 격하된 `G*-a`의 후단 부속절**이다.
2. Step 2의 실질 판정은 **G2-b·G2-c·G2-d 세 개의 독립 게이트**가 지고 있고, 셋 다 내 실측상 실제로 깨진다.
3. 놓칠 수 있는 것이 **남은 미사용 import(MINOR)** 뿐이고, 계획이 삭제/잔존 import를 **이름까지 열거**해 두어 `git diff` 대조가 컴파일러 경고보다 **더 강한 검사**로 이미 가능하다.
4. 즉 **material한 주장에 거짓 그린을 낼 수 있는 구조가 아니다.** D 조항의 취지(거짓 그린 방지)에 실질적 위배가 없다.

## 이슈 / 리스크

1. **[지적 · 조건 C-1] G2-a 후단이 공허한 조건이다.** 실측 근거는 위 §4. `git diff`의 import 블록 대조로 대체하면 해소된다.
2. **[보강 · 조건 C-2] G4-a의 RED 증명이 케이스 1만 커버한다.** 케이스 2(null 분기)는 "예외 없이 반환한다"는 약한 단정이라 RED 증명이 특히 필요하다. `?.`를 `!!`로 바꿔 NPE가 나는 것으로 증명하면 **R-P6(`?.`→`!!` 변질)과 R-P7(null 분기 누락)을 같은 동작으로 동시에 방어**한다.
3. **[남는 해석 여지 — developer를 막지 않음] E-2(b).** 리드의 확정 해석 "파일 위치(및 패키지)" + "두 클래스 모두 이동 대상"을 "두 클래스 모두 패키지를 바꾼다"로 읽는 것도 문언상 불가능하지 않다. 나는 사용자 원문의 지시 대상("App Class에 있는")을 근거로 그 독법을 택하지 않았고 **임의로 좁힌 것이 아니라고 판정**했다. 다만 유일한 독법이라고 주장하지는 않으므로, 전환 비용을 미리 계산해 evaluation.md §1-E2c에 적었다 — 파일 이동 + `package` 1줄 + 제외 패턴 1줄 + 주석. **파이프라인 재실행 없이 소규모 후속 배치로 처리 가능하다.** 확인이 필요하면 오케스트레이터가 4단계와 **병렬로** 물으면 된다.
4. **[재현하지 않은 항목] R-P3(낡은 `.class` 오염).** 재현하려면 실제로 클래스를 옮겨야 하는데 evaluator는 코드를 고치지 않는다. **판정에 영향 없다** — `clean` 추가는 무조건적으로 안전한 완화책이고(틀린 수치를 만들 수 없다), `clean jvmCoverageReport --rerun-tasks`가 베이스라인을 **두 JDK에서 각각 재현**함을 확인했다.
5. **[사소한 불일치] `App.kt` 총 라인.** 계획은 169줄, `wc -l`은 168줄(파일 끝 빈 줄 처리 차이). G2-b 판정에 영향 없다.
